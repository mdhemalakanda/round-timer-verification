6.7 Round timers & access windows — verification report

Requirement: docs/COMMERCIAL-VERSION-REQUIREMENTS.md § 6.7 (FR-TIME-1 … FR-TIME-4) · Site: http://localhost:10063 · Date: 23 Sep 2026 · Test account: roundtimer-uat (user 496) through the real WooCommerce order pipeline.
6.7 requirement summary. Initial payment covers rounds 1–3 with a maximum 30-day window that starts only when the participant completes their first-round tests — never at payment. Each continuation payment covers 2 rounds (4–5, 6–7 …) with a 21-day window that starts at payment. The sidebar shows a visible countdown for the active block. The progress questionnaire is available only in the final round of a block and only after 8 days into that round; recommended pace 8 days per round is shown as guidance.

FR-TIME-1 — Initial block (rounds 1–3), timer starts at first-round completion

1.1 Payment + initial questionnaire done, round 1 entered → no countdown yet

Participant entered Round 1 (initial questionnaire submitted, test 1A1 rendered). The sidebar has no countdown line: the 30-day window is still pending because Round 1 has not been completed yet. Verified in bt_course_blocks: window_started_at = NULL.

1.2 Round 1 tests completed → the 30-day window starts and the countdown appears

As soon as Round 1 is completed (round-end logic: per-round test limit / 3–4 rating threshold reached), the pending window starts: window_started_at = completion moment, window_ends_at = +30 days. The sidebar now shows the countdown (FR-TIME-3) and the round-complete notice explains the 8-day pace ("Kahdeksan päivän kuluttua…"). Verified programmatically: window_ends_at − now ≈ 30 days.
Implementation. Blocks are stored with the first_round_tests_completed trigger and a pending window. CourseBlockAssigner::start_pending_window_on_round_completion() listens to bt_round_tests_completed (fired by RoundLimits when Round 1 ends) and starts the window only when the completed round equals the block's first round. Access stays open while the window is pending; once started it is enforced by ContinuationFlow::can_enter_round() via get_active_granted_round() — expired windows lock their rounds.

FR-TIME-2 — Continuation blocks (2 rounds), 21 days from payment

Right after the continuation order (79 € product) completed, block 4–5 was provisioned with window_started_at = payment moment and window_ends_at = +21 days; the sidebar countdown shows 21 days and Round 4's test is immediately accessible. Verified programmatically: |window_ends_at − (now + 21 days)| < 2 h, and Round 6 stays locked until the next payment.

FR-TIME-3 — Visible sidebar countdown

The sidebar countdown renders the exact client string "Sinulla on X päivää aikaa suorittaa nämä kierrokset loppuun." from the current block's active window (screenshots 02 and 05 show it live at 30 and 21 days). It is hidden while no window is pending/active (screenshot 1.1) and disappears when the window expires — at which point the block's rounds are locked (can_enter_round() false, tests closed), as verified programmatically by backdating the window.

FR-TIME-4 — Questionnaire gate: only in the final round, only after 8 days

4.1 Final round in progress, < 8 days → check-in locked

Participant is in the block's final round (round start recorded). The Edistyminen tab shows no questionnaire form: the gate (RoundLimits::is_final_round_checkin_due()) requires round_start + 8 days — and the round's tests to be completed. Round starts are recorded automatically whenever test_round advances (bt_round_started_at user meta).

4.2 Final round, > 8 days → check-in unlocks automatically

Same participant with the round start backdated 9 days (the phpMyAdmin fast-forward from the manual guide): the questionnaire opens without any email link, filled, and advances the participant. For non-final rounds the existing invite / auto-access pacing is retained, retuned to 8 days (round end schedules the bt_continuation_round_invite event at the recommended delay). Admin override is preserved: "Grant progress access" on the Users Progress screen and the manual meta grant both open the check-in regardless of the gate.

Admin configuration — Tests → Settings

New section "Round timers & access windows": the initial and continuation window durations are admin-configurable (defaults 30 / 21, validated 1–365). A saved duration is authoritative for newly purchased blocks — product meta and code constants apply only when unset — so fast testing is possible (set 1 day) without database access. The existing fields above it (round invite delays, auto access, course end date) drive the FR-TIME-4 non-final pacing and the legacy countdown. The per-round 8-day questionnaire pacing lives in Test Management ("Min days for questionnaire").

Bugs found and fixed during this verification round: fresh participants' ratings landed in "round 0" (so the 30-day timer never started — FR-TIME-1), the final-round check-in could be submitted before the round's tests were done, a full progress delete left the old timers running (FR-TIME-1 restart), and the window durations were not admin-configurable. All fixed in this release and covered by the suites above.
